# 服务端设计决策与背后的思路

> 这份文档写给**从客户端转过来的工程师**：代码在 `src/`，这里是「为什么这么写」。
> 每个决策按同一结构写：**遇到什么问题 → 有哪些备选 → 为什么选这个 → 代价是什么**。
> 看懂"代价"比看懂"选择"重要——服务器设计没有免费的正确，只有明确的取舍。

## 先记三句话

1. **客户端是表现，服务器是权威。** 客户端说什么都不算数，服务器必须自己再算一遍。
2. **服务器的 bug 会累积，客户端的 bug 会重启。** 内存、会话、线程，漏一点就永远漏着。
3. **服务器最贵的不是 CPU，是"不可预测"。** 一个玩家的行为不能影响其他人的延迟。

---

## D1 · 为什么是 UDP + KCP，而不是 TCP 或纯 UDP

**问题**：实时位置同步，每秒几十次小包。

- **TCP**：可靠有序，但丢一个包会让**后面所有包排队等它重传**（队头阻塞）。玩家会看到"卡一下然后瞬移"。
- **纯 UDP**：没有队头阻塞，但要自己实现重传、去重、乱序重排、拥塞控制——这是一篇论文的工作量。
- **UDP + KCP**：KCP 是"跑在 UDP 上的 ARQ 协议"，用**更高带宽**换**更低延迟**（激进重传、快速重传、可关拥塞控制）。

**选了 KCP**，代价是：你得自己维护会话状态、NAT 超时、以及"连接"这个概念（UDP 没有连接）。

**但登录、配置、公告、热更清单为什么还是走 HTTP？**
因为那里要的是**可靠 + 简单 + 可缓存 + 能被网关/CDN 处理**，而不是 20ms 的延迟。用 KCP 传一个 10KB 的 JSON 配置是自找麻烦。

> **思路**：协议不是信仰，是匹配场景。低延迟有状态走 UDP，一次请求一次响应走 HTTP。

## D2 · 为什么一条连接对应一个"会话对象"

**问题**：服务器同时面对上千个玩家，状态放哪？

**备选**：一张全局大表（所有玩家的位置都存在一个 Dictionary 里）／每个连接一个对象。

**选了「每个连接一个对象」**（`NetSession`）。因为：
- **隔离**：一个会话的状态（KCP 序号、重传队列、接收缓冲）内聚在它自己身上，不会互相污染。
- **所有权**：这份状态只有一个"主人"（见 D3），不需要加锁。

> **思路**：这是服务器最基础的思维——**把「共享」变成「独占」**。共享得越少，能出错的地方越少。业界把它叫 Actor 模型 / 单所有权（single ownership）。

---

## D3 · 为什么要"定频泵 + 单线程"（本仓库最核心的一条）

**问题**：KCP 内部是链表 + 序号（`_sndBuf`、`_sndQueue`），被两个线程同时改就会链表断裂、序号错乱——这种崩法**不会立刻报错，只会在几分钟后表现成"莫名丢包"**。

**三种解法**：

| 方案 | 问题 |
|---|---|
| 加锁 | 锁粒度几乎不可能调对：锁粗了吞吐崩，锁细了漏字段。而且锁竞争本身就在吃延迟 |
| 每个会话一个线程 | 上千会话 = 上千线程。上下文切换、缓存失效、内存爆炸 |
| **单线程轮询所有会话** | 所有会话在**同一个线程**上推进，天然无锁 |

**选了第三种**：`ServerLoop` 每 10ms 醒来一次，把收到的包分给对应会话、推进所有会话的 KCP、处理到期的重传。这叫 **tick loop（定频泵）**。

定频带来三个好处：
1. **延迟可预测**：最坏情况是"多等一个节拍"（10ms），不是"等锁"。
2. **顺序确定**：同一个 tick 内，先处理 A 再处理 B 是确定的，bug 可复现。
3. **可批处理**：一次 flush 把多个包塞进一个 UDP datagram，省带宽。

**代价**（必须记住）：
- **任何人阻塞，全员卡住**。所以处理器里禁止 `Thread.Sleep`、同步 IO、长锁——这就是 README「线程模型」那张表的由来。
- **单核上限**。一个进程只能用一颗核跑逻辑。真到瓶颈时按"分片"扩（见 D11 的演进）。

> **思路**：服务器性能的第一杀手不是"算得慢"，是"不可预测"。定频泵用一点吞吐换来了确定性，这在实时游戏里是划算的。

## D4 · 为什么按「端点」而不是 conv 建会话（一次真实的坑）

**协议事实**（客户端代码）：

```csharp
private uint _nextConv = 1;              // NetworkManager
private uint AllocateConv() => _nextConv++;
```

conv 是**进程内自增**的。也就是说——每个玩家进程的第一个会话，conv 都是 `1`。

**如果服务端按 conv 建会话**：玩家 A 和玩家 B 都送来 `conv=1`，服务端会把它们当成同一条通道 → **两人互相收到对方的消息**。这种 bug 在测试环境（一个人测）永远不出现，上线才炸。

**选了按 `IPEndPoint`（ip:port）建会话**，conv 只用于"同一端点内检测通道重建"。

> **思路**：**不要用"看起来唯一"的字段做唯一键，要问"它的生成域是什么"**。conv 的生成域是"进程"，端点的生成域是"整个网络"。

## D5 · 为什么是"首包建会话"，代价是什么

协议里**没有 connect 包**：客户端 `Connect()` 之后立刻认为自己是"已连接"。UDP 也没有三次握手。

所以服务端只能**等第一个数据报到达**才知道"来了个玩家"。客户端心跳每 5s 一次，所以最迟 5s 内一定会建会话。

**代价**：服务端无法在"连接建立那一刻"做鉴权、限流、分配 ID——只能在**首包之后**做。

**这就是为什么要有握手（opcode 4/5）**：用应用层的 token 校验补上传输层缺失的"准入"环节。TCP 世界这件事发生在握手时，UDP 世界只能自己造。

> **思路**：协议缺什么能力，就在应用层补一个；补的时候要想清楚"补在哪一步、失败怎么回"。

---

## D6 · 为什么拒绝握手要"延迟 0.2 秒关闭"

**问题**：握手校验失败，要回一个 `HandshakeResult(code=1, reason)` 然后关会话。

**天真写法**：发完立刻 `Close()` → 会话被移出路由 → **下一个 tick 不再冲刷 KCP** → 那个拒绝包永远发不出去 → 客户端只会看到"握手超时"，而不是"你 token 错了"。

**选了 `RequestClose(reason, delaySeconds: 0.2)`**：先标记"本会话待关闭"，让泵继续冲刷 0.2 秒（约 20 个节拍），再真正关闭。

> **思路**：**"说再见"本身也是一次发送**。关连接是异步的，凡"发完就关"的地方都要问一句：数据冲刷出去了吗？

## D7 · 为什么 KCP 参数必须两侧完全一致

| 参数 | 作用 | 不一致的后果 |
|---|---|---|
| `Mtu` | 一个段多大（分片大小） | 一边 512 一边 1200 → 大消息的段数超过对端窗口 |
| `SndWnd/RcvWnd` | 同时在途多少段 | 窗口太小 → 带宽跑不满；差太多 → 大消息卡死 |
| `Interval` | 内部冲刷间隔 | 影响重传节奏与延迟 |

所以 `KcpSettings` 的默认值被**逐项对齐**客户端 `NetworkSettings`，并在 `Validate()` 里拦住越界值（见 D10）。

> **思路**：**协议参数是契约的一部分**。它一旦进了协议层，就不能单方面改——这跟"客户端改个 UI 颜色"完全不是一类事。

---

## D8 · 为什么版本号要跟着客户端包走

大多数项目的服务端有自己的版本线（1.4.2 之类）。这个项目**刻意不这么做**：

```
服务端 Version == cn.efefef.net 的 package.json version
```

因为**它不是独立产品，是同一个协议的另一端**。当线上出问题时，第一句话是"你客户端哪个版本"，那么服务端版本必须能直接回答"我支持哪个协议能力"。

实现上只有**一个来源**：`Directory.Build.props` 的 `<Version>`，由 `tools/sync-protocol.py --check` 校验与包版本一致——写错就构建失败，不靠自觉。

> **思路**：**能自动校验的约定才是约定，写在文档里的叫愿望**。

---

## D9 · 为什么协议文件"单向同步 + 禁止手改"

`src/EFramework.Net/Protocol/` 下 4 个文件是从 Unity 包**逐字节复制**的，文件头有 `SyncedFrom` 标记。

**为什么不做两份实现**（服务端自己写一份 KCP）：
因为**双份实现必然漂移**。今天你改一个边界判断，明天他改一个重传条件，三个月后两侧行为不一致——而症状是"偶发丢包"，排查成本高到离谱。这是行业铁律：**不要手写两份协议/序列化**。

**代价**：改协议必须两端一起发版。所以 `CONTRIBUTING.md` 规定"协议层改动 = breaking"，且同步脚本会在内容漂移时直接失败。

> **思路**：**单一真相源（single source of truth）**。宁可多一步同步脚本，也不要两份"看起来一样"的代码。

---

## D10 · 为什么大量"启动期校验"和"立即失败"

服务器最怕的不是崩溃，是**静默错误**：

| 静默错误 | 表现 | 我们的处理 |
|---|---|---|
| `Mtu` 写成 1 | `Kcp.SetMtu` 抛异常，而调用点在"首个数据报→会话构造"上 → **每个包抛一次**，被泵吞掉继续跑 | `KcpSettings.Validate()` 在 `new NetServer()` 时抛，启动就失败 |
| 窗口写 70000 | 段头里是 uint16 → **静默截断**成错误窗口通告 | 校验 1..65535 |
| 跨线程 `Send` | 破坏 KCP 链表，几分钟后才表现成丢包 | `NetSession.Send` 自动排队；`NetServer.Send` 直接抛异常 |
| 默认参数被就地修改 | `KcpSettings.Default.Mtu = 470` 会静默影响**此后新建的每个会话** | 宿主 `Clone()` 一份自用，断开共享 |

> **思路**：**能在启动期发现的，绝不留给运行期；能在调用点发现的，绝不留给数据**。
> 反过来说：一条"每包打一条错误日志"的路径，是最糟的——它把配置错误伪装成了运行时噪音。

## D11 · 为什么入站用缓冲池、出站用会话私有缓冲

内存所有权有三种模型，选错就漏：

| 模型 | 谁负责释放 | 适用 |
|---|---|---|
| 谁分配谁释放 | 分配方 | 生命周期完全在一个函数内 |
| **借用 + 显式归还** | 消费方（必须） | 生命周期跨组件边界 |
| **池化复用** | 持有者长期持有 | 高频、大小可预测 |

- **入站**：套接字收到包 → 传输层分配 → **泵消费** → `finally` 归还 `ArrayPool`。生命周期跨越两个组件，所以必须显式 `Release`（用 `finally` 保证不泄漏）。
- **出站**：会话自己持有一个按需扩容的帧缓冲，`Send` 内部写完就交给 KCP（KCP 会再拷进段）。生命周期完全在函数内，所以最简单——**不需要池，也不需要归还**。

**为什么入站载荷还要拷贝一次**（`NetPacket.Payload`）？
因为 handler 可能想持有它。省下这一次拷贝，就得把语义改成"借用会话缓冲、下条消息到达即失效"——那是**破坏性变更**，为每消息几十字节不值。

> **思路**：**先问生命周期，再选所有权模型**。绝大多数内存 bug 不是"忘了 free"，是"所有权没想清楚"。

## D12 · 为什么 HTTP 不开在消息泵里

HTTP 是"请求来了就处理、处理完就回"，天然是异步并发的；泵是"每 10ms 推进一次所有会话"，天然是同步单线程的。

塞进去只有两条路：阻塞泵（所有人卡住），或者让泵异步化（失去无锁这个前提）。

**选了同进程、两个宿主**：Kestrel 在自己的线程池上跑，通过 `Post` / `PostAsync` 和泵对话。

```csharp
// 命令：单向投递，下一个节拍执行
server.Post(s => s.Broadcast(opcode, payload));

// 查询：投递并等结果（≤1 个节拍），因为会话字典只有泵线程能读
var stats = await server.PostAsync(s => s.SessionCount);
```

**为什么不抽象成"统一传输层"**：`IServerTransport` 是**报文语义**（一次一条、非阻塞、无连接），HTTP 是**流语义**（连接复用、请求边界、背压）。硬统一只会得到一个"两边都不好用"的最小公倍数接口。正确的复用层次是**领域层**，不是传输层。

> **思路**：**隔离失败域比减少进程数重要**。同进程是为了省部署成本，不是为了共享线程。

## D13 · 服务器思维速查表（客户端视角对照）

| 概念 | 一句话解释 | 本仓库对应 |
|---|---|---|
| 权威服务器 | 客户端只做表现，校验全在服务端 | handler 里重新算 |
| Tick / 定频 | 服务器按固定节拍推进世界 | `ServerLoop` 10ms |
| Actor / 单所有权 | 一份可变状态只有一个线程能改 | 泵线程独占会话 |
| 背压 | 消费不过来就丢/降级，别无限排队 | `ReceiveQueueCapacity` 满则丢 |
| 心跳 / 超时回收 | 一段时间没动静就当它死了 | 客户端 5s Ping / 服务端 30s 回收 |
| 优雅停机 | 先停入口（不再收新），再关存量 | `StopAsync` 顺序 |
| 观察面 | 没有监控的服务器等于没有服务器 | `/stats` `/sessions` |
| 幂等 | 同一个请求重发多次，结果不变 | ⚠️ 尚未实现（见下） |
| 限流 | 保护自己不被单个客户端打满 | ⚠️ 只做了会话数上限 |

## 目前这套架构的短板（诚实清单）

| 短板 | 风险 | 怎么补 |
|---|---|---|
| 无鉴权 | 谁猜中端口都能连 | 实现 `IHandshakeValidator`（验签/有效期）+ `RequireHandshake=true` |
| 无加密 | UDP 明文可被读取/篡改 | 帧层加签名，或换 DTLS |
| 无持久化 | 重启即失忆 | 加数据库/Redis，登录态落地 |
| **无 RPC 幂等** | 重连后客户端重发 → **同一请求执行两次**（扣两次钱那种） | 请求序号 + 服务端去重缓存 |
| 单核上限 | 一个进程只能用一个核 | 分片：按 sessionId 哈希分到多个泵（多进程/多线程各管一片） |
| `/admin/*` 无鉴权 | 能广播、能踢人 | `RequireAuthorization()` + 限流 |

**建议的学习顺序**（边读代码边做）：
1. 读 `Kcp.cs` 的 `Flush` / `Input` / `Update` —— 理解"重传是怎么发生的"。
2. 读 `SessionRouter` / `ServerLoop` —— 理解"一个线程怎么服务上千连接"。
3. 自己加一条业务消息（`CONTRIBUTING.md` §6）—— 走通全链路。
4. 加鉴权 → 加持久化 → 加幂等 —— 这三个补完就是能上线的后端。
5. 用 `probe` 加压测（改造成循环发 1 万个包）—— 看 `WaitSnd` 和延迟。

## 术语表

| 术语 | 含义 |
|---|---|
| **ARQ** | Automatic Repeat reQuest，自动重传请求。KCP 的核心机制 |
| **RTT / RTO** | 往返时间 / 重传超时。RTO 是"等多久没 ACK 就重发" |
| **MTU / MSS** | 一个 UDP 包的最大字节数 / 其中能装数据的部分（= MTU − 24 字节段头） |
| **快速重传** | 收到 N 个重复 ACK 就立刻重发，不等超时（`FastResend=2`） |
| **队头阻塞** | 前面一个包丢了，后面全得等——TCP 的固有问题 |
| **conv** | KCP 的会话号，收发双方必须一致，否则段会被丢弃 |
| **会话（session）** | 服务端对"一个远端玩家"的全部状态：KCP 实例、收发计数、状态机 |
| **端点（endpoint）** | ip:port。网络层唯一身份 |
| **背压** | 上游太快、下游处理不过来时的策略：丢弃、降级或阻塞源头 |
| **幂等** | 同一操作执行多次与执行一次结果相同 |
| **优雅停机** | 先停止接收新请求，等存量处理完，再释放资源 |
| **观察面** | 能从外部看到内部状态的能力（指标、日志、健康检查） |
| **单所有权** | 一份可变状态只允许一个线程写，从根本上消灭数据竞争 |

## 这份文档怎么维护

- 新增**架构级**决策（换协议、改线程模型、拆进程、加缓存层）时，在本文加一节 `D<n>`，按"问题→备选→选择→代价"四段写。
- 代码里引用决策时写 `见 docs/design-decisions.md D3`，不要复述。
- **代价**那段不能省：省了它就变成了宣传稿，三个月后没人记得为什么这么选。
