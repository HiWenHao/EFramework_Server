# HTTP 接口：契约 → 双端代码生成

> 一份 JSON 契约，一条命令，生成服务端与客户端的类型、路径常量、调用封装。
> 手写的只有业务实现，生成物永远不被覆盖。

## 0. 为什么不让两端各写一遍

同一个接口，服务端写一遍 DTO、客户端再写一遍，**一定会漂移**：某个字段改名、`int` 变 `long`、
某个字段忘了带 `camelCase` —— 编译器不会报错，只有线上 400 或反序列化失败会。

这跟协议层「不要手写两份 KCP」是同一条纪律：**单一真相源 + 生成 + 漂移即失败**。

所以仓库里有两条同步链，哲学完全一致：

| 层 | 真相源 | 工具 | 漂移检测 |
|---|---|---|---|
| UDP 协议 | Unity 包 `cn.efefef.net` | `tools/sync-protocol.py` | `--check` 退出码 1 |
| HTTP 接口 | `contracts/*.json` | `tools/gen-http-api.py` | `--check` 退出码 1 |

## 1. 一条命令

```bash
python tools/gen-http-api.py            # 生成全部契约
python tools/gen-http-api.py --check    # 只校验；有漂移退出码 1（挂 CI）
```

生成位置：

```
服务端  src/EFramework.Http/Api/Generated/<Api>.Contracts.g.cs   DTO
        src/EFramework.Http/Api/Generated/<Api>.Endpoints.g.cs   路径常量 + I<Api> + Map<Api>()
客户端  Assets/NetApi/Generated/<Api>.Contracts.g.cs             DTO
        Assets/NetApi/Generated/<Api>.Client.g.cs                路径常量 + <Api>Client
```

幂等：重复执行不产生差异；`--check` 在干净状态下返回 `[OK] generated code is up to date`。

## 2. 契约怎么写

```json
{
  "api": "LoginApi",
  "title": "登录与配置",
  "endpoints": [
    {
      "id": "Login",
      "method": "POST",
      "path": "/api/login",
      "summary": "账号密码登录，返回握手票据",
      "request":  { "type": "LoginReq", "fields": [ {"name":"Account","type":"string","comment":"账号"} ] },
      "response": { "type": "LoginRes", "fields": [ {"name":"Code","type":"int","comment":"业务码"} ] }
    }
  ]
}
```

| 字段 | 说明 |
|---|---|
| `api` | 生成类名前缀：`ILoginApi` / `LoginApiRoutes` / `LoginApiEndpoints` / `LoginApiClient` |
| `id` | 生成方法名：`Login` → `LoginAsync`；也是路径常量的名字 |
| `method` | **v1 只支持 GET / POST**（见 §6） |
| `request` | 可省略（GET 必须省略；写了会直接报错） |
| `response` | 必填 |
| `type` + `fields` | 字段类型：`string / int / long / float / double / bool`，`"nullable": true` 生成 `int?` |

JSON 线上格式固定 **camelCase**：服务端生成 `[JsonPropertyName("account")]`，客户端生成
`[JsonProperty("account")]` —— 两侧序列化器不同（System.Text.Json vs Newtonsoft），但字节一致。

## 3. 生成什么 / 手写什么

| 归属 | 内容 | 会被覆盖吗 |
|---|---|---|
| **生成** | DTO（含 JSON 特性、双语注释） | 会 —— 改契约后重新生成 |
| **生成** | 路径常量 `LoginApiRoutes.Login` | 会 |
| **生成** | 服务端接口 `ILoginApi` | 会 |
| **生成** | 服务端路由映射 `MapLoginApi(app, api)` | 会 |
| **生成** | 客户端强类型封装 `LoginApiClient.LoginAsync(...)` | 会 |
| **手写** | 服务端实现 `LoginApi : ILoginApi`（`src/EFramework.Http/Api/LoginApi.cs`） | **不会** |
| **手写** | 客户端调用点 `new LoginApiClient(baseUrl).LoginAsync(...)` | **不会** |

生成物头部有 `Generated by: tools/gen-http-api.py from contracts/login.json` 与「请勿手改」。
**生成器不猜业务**：它只负责"路由长什么样、类型长什么样"，一旦开始生成业务逻辑就会退化成不可维护的
模板引擎。

## 4. 一个真实例子：登录发票据 → 连 UDP

`contracts/login.json` 里两个端点，服务端实现在 `Api/LoginApi.cs`，链路是：

```
客户端 POST /api/login {"account":"demo","password":"demo"}
  → 服务端校验 → 用服务端密钥签 HandshakeToken
  → 返回 {"code":0,"token":"demo:1794560062:14b1...","expiresAtUnix":1794560062}
客户端 NetworkManager.Instance.Connect(host, port, token)
  → 游戏服验签 → [SESSION 1] handshake accepted as demo
```

实测（2026-11-13，本机）：

```
POST /api/login  →  {"code":0,"token":"demo:1794560062:14b1...","serverVersion":"0.0.2"}
POST /api/login  →  {"code":2,"message":"invalid account or password"}      ← 密码错，HTTP 仍 200
probe 127.0.0.1 7777 "<token>"
  [OK] Handshake code=0
  [OK] Pong 29ms
  [OK] EchoRes ...
服务端日志：[HTTP] login ok: account=demo → [SESSION 1] handshake accepted as demo
```

这就是"登录走 HTTP、玩法走 UDP"的最小闭环：**游戏服只验签，签发权只在登录侧**（见 D14）。

## 5. 业务失败怎么表达

**HTTP 状态码只表达传输层结果**（200 成功、400 请求格式错、500 服务端炸了），
**业务结果放 body 里的 `Code` / `Message`**。

原因：客户端拿到 401 只能提示"网络错误"，而"账号密码错""票据过期""被封禁"是三种完全不同的处理
（重试 / 重新登录 / 提示联系客服）。把业务码塞进 HTTP 状态码，客户端就得维护一张状态码 → 文案的映射表，
还要担心网关/代理改写状态码。

所以生成的端点**永远返回 200**（除非实现返回 null，此时 500 表示"实现 bug"）。

## 6. v1 不支持什么（以及怎么办）

| 不支持 | 原因 | 怎么办 |
|---|---|---|
| PUT / PATCH / DELETE | 客户端 `HttpManager` 的泛型重载只覆盖 GET/POST；生成半成品 API 比不支持更糟 | 改成 POST（推荐），或手写 wrapper 调 `PutAsync` |
| 数组 / 嵌套对象 | 需要额外描述元素类型，契约复杂度陡增 | 先用 JSON 字符串字段过渡，需要时再扩展生成器 |
| 查询参数 / 路径参数 | 路径拼装与转义容易出错，且客户端 URL 编码要单独测 | 用 POST + body；确需 RESTful 时手写端点 |
| 枚举 | Unity 与 .NET 的枚举序列化行为不一致（数字/字符串） | 用 `int` + 客户端映射表 |
| 鉴权 / 限流 | 属于宿主中间件，不是"接口形状" | `MapGroup(...).RequireAuthorization()`（见 README 约束 §8） |

**加一个不支持的写法会直接报错**（而不是静默生成不可用的代码）——这是刻意设计：宁可生成失败，
也不要让"看起来能用"的代码流进去。

## 7. 新增一个接口的标准流程

```bash
# 1. 改契约
vim contracts/login.json

# 2. 生成（服务端 + 客户端）
python tools/gen-http-api.py

# 3. 服务端补实现（实现 ILoginApi 的新方法）
vim src/EFramework.Http/Api/LoginApi.cs

# 4. 接线（如果新增 api 文件）
vim src/EFramework.App/Program.cs   # web.MapLoginApi(new LoginApi(...));

# 5. 验证
dotnet build EFramework_Server.sln
python tools/gen-http-api.py --check
```

客户端拿到新的 `LoginApiClient` 方法即可直接调用，**不需要手写 DTO**。

## 8. 排查

| 现象 | 原因 | 处理 |
|---|---|---|
| `--check` 报 DRIFT | 改了契约没重新生成，或手改了生成物 | 重新跑生成器；手改的内容挪到实现类 |
| 客户端找不到 `LoginReq` 类 | 没生成到 Unity 工程，或 Unity 没刷新 | 看 `Assets/NetApi/Generated/` 是否存在；Unity 里右键 Reimport |
| 服务端 400 找不到请求体 | 客户端发的 JSON 字段名不是 camelCase | 检查 DTO 上的 `[JsonProperty]`；契约改字段名后必须重新生成 |
| 客户端反序列化出 null | 服务端字段名与契约不一致 | `python tools/gen-http-api.py --check` 确认两侧同源 |
| 新增接口返回 500 | 实现里返回了 null，或抛异常 | 看服务端日志；实现必须返回非 null DTO（业务失败用 `Code`） |
