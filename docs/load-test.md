# 压测方法与实测结论

> 这份文档有两半：**怎么测**（方法）和**测到了什么**（数据 + 结论）。
> 读的时候请重点看「这些数字不能说明什么」——新手最容易把 loopback 的延迟当成产品延迟。

## 0. 一句话结论

**在单机 loopback 上，服务端处理 10k 消息/秒时泵只用了 7% 的算力，没有丢一个包、没有一次处理失败。**
延迟数字（p50 20~60ms）**不能**当作产品延迟：它主要由两侧各一个 KCP 冲刷间隔、Windows 计时器精度
和压测工具自身的调度噪声构成。

## 1. 工具怎么用

压测工具就是验证工程的一个模式，它复用与服务端对端**完全一致的协议栈**（`ProtocolClient`），
只多了限速与 RTT 统计。

```bash
# 业务路径：100 个客户端，每个每秒 10 条（总 1000/s），跑 10 秒
dotnet run --project tests/EFramework.Tests -- load 127.0.0.1 7777 \
    --clients 100 --qps 10 --seconds 10 --stats-url http://127.0.0.1:8080/stats

# 协议下限：同样速率但只走 Ping/Pong（不反序列化 JSON）
... --mode ping

# 想压更高吞吐就加生成器线程（单线程生成器在几百 socket 时会先饱和）
... --clients 800 --qps 12.5 --threads 4
```

| 参数 | 说明 |
|---|---|
| `--clients` | 并发客户端数（= 并发会话数） |
| `--qps` | **每个客户端**每秒多少条；总速率 = clients × qps |
| `--seconds` | 计时窗口（预热与收尾不计入） |
| `--mode` | `echo`（默认，1001→1002，走 JSON + 分发器）/ `ping`（1→2，只走协议栈） |
| `--size` | 业务请求里 JSON 的填充长度 |
| `--threads` | 生成器线程数（默认 1） |
| `--token` | 服务端开鉴权时的握手票据 |
| `--stats-url` | 服务端 `/stats`，用于和客户端结果对账 |

输出里最重要的一行是 `server ... handled +N`：**它必须等于客户端的 `recv`**，否则说明有消息被静默丢弃。

## 2. 三次测量，三个结果（这一节比数据更重要）

同一份服务端代码，只改**测量方式**，p50 就从 63ms 变成 22ms：

| 阶段 | 改了什么 | p50 | 说明 |
|---|---|---|---|
| A | 初版生成器（`Thread.Sleep(1)` 轮询） | 63.47ms | 把生成器自己的唤醒延迟算进了 RTT |
| B | 生成器改为自旋（有在途消息就 `Sleep(0)`） | 36.10ms | 少了 27ms，全部是测量误差 |
| C | 服务端把「冲刷」移到节拍末尾 | **22.08ms** | 少了 14ms，这是**真实**的服务端改进 |

**教训**：先确认"测量工具不是瓶颈"，再谈优化。B 阶段省下的 27ms 一行服务端代码都没改。

## 3. 实测数据（本机：28 逻辑核，Windows 11 24H2，loopback）

| # | 客户端 | 单连速率 | 总速率 | 模式 | 生成器线程 | p50 | p95 | p99 | 丢包 | 服务端（节拍/每拍工作） |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 | 100 | 10/s | 1 000/s | echo | 1 | 21.7ms | 38.0 | 41.7 | 0% | 15.6 / — |
| 2 | 100 | 100/s | 10 000/s | ping | 1 | 20.3ms | 39.4 | 46.6 | 0% | 15.62 / 0.29ms |
| 3 | 400 | 25/s | 10 000/s | echo | 1 | 46.7ms | 84.9 | 103.5 | 0% | 15.4 / — |
| 4 | 400 | 25/s | 10 000/s | ping | 1 | 43.6ms | 99.3 | 122.6 | 0% | — |
| 5 | 800 | 12.5/s | 10 000/s | ping | 4 | 60.5ms | 122.1 | 145.8 | 0% | 16.41 / 1.16ms |
| 6 | 800 | 2/s | 1 600/s | ping | 4 | 39.9ms | 73.0 | 83.5 | 0% | 10.36 / 0.08ms |

### 从表里能得出的（可信）

1. **零丢包、零处理失败**，且客户端 `recv` 与服务端 `handled` **逐条相等**（如 100 800 = 100 800）。
   说明背压、限流、缓冲池、路由都没有吞消息。
2. **泵不是瓶颈**：10k msg/s 时每拍只花 1.16ms（16.4ms 节拍里占 7%）。按线性外推，泵的算力上限
   在 10 万级 msg/s，但这只是外推——**没有实测**，因为生成器先跑不动了。
3. **同等 10k/s，100 会话比 800 会话延迟低一半**（20ms vs 60ms），而服务端工作量只从 0.29ms 涨到 1.16ms。
   差额不在服务端，在生成器与内核收发路径（每个 socket 一次系统调用、4 个自旋线程抢占调度）。
4. **ping 与 echo 延迟几乎相同**（20.3 vs 21.7 / 43.6 vs 46.7）：说明在 10k/s 这个量级上，
   JSON 序列化 + 分发器**不是**成本主体。

### 从表里不能得出的（别误读）

1. **不能当产品延迟**。这里是 loopback，RTT 里装着两次 KCP 冲刷间隔（各 ~10-15.6ms），
   真实网络还要加 RTT/2。产品延迟要按「客户端帧时间 + tick + 网络」估，不是这个数。
2. **不能当连接数上限**。800 是我这台机器的生成器能撑住的上限，不是服务端的。
   要测连接上限，得把生成器拆到另一台机器（或另起一个进程跑多个生成器实例）。
3. **不能横向比机器**。生成器与服务端抢同一台机器，数字偏保守且噪声大。
4. **不能推出"tick 越小越好"**。tick 变小省延迟，但每拍预算也变小；当 `每拍工作 ≥ 节拍` 时就翻车。

## 4. 两个真实的服务端改进（由压测驱动，不是拍脑袋）

### 4.1 冲刷顺序：白送一个节拍的延迟

原来 `NetSession.Tick` 的顺序是「先 `Kcp.Update()` 冲刷 → 再取包派发」，于是本拍产生的回包要等到
**下一拍**才冲刷出去，白送一个 `TickIntervalMs`（实测 14ms）。

改成「先取包派发 → 最后统一冲刷」后，回包在同一个节拍发出。这条改动对**所有** RTT 敏感的业务都生效。

### 4.2 节拍精度：配置 10ms，实际 15.6ms

Windows 默认计时器周期约 15.6ms，`WaitOne(10)` 会真的睡 15ms。实测「配置 10ms、实际 15.78ms」。
后果不只是延迟偏高：`TickIntervalMs` 相关的所有承诺（超时判定、延迟上限）都失真。

处理：
- 启动时尝试 `timeBeginPeriod(1)`（`HighResolutionTimer`，默认开）；
- **无论是否生效，都把实测值暴露出来**：`/stats` 的 `actualTickIntervalMs`、`actualTickWorkMs`；
- 实测值超过配置 1.5 倍时**打一条 Warn**，直接告诉你换 `TickIntervalMs >= 16` 或换 Linux。

> 教训：**别让参数撒谎**。配置项和实测值必须都可观测，否则调参就是在猜。

## 5. 运维该盯哪个指标

不是 msg/s，是 **`actualTickWorkMs / tickIntervalMs`（泵利用率）**：

| 利用率 | 含义 | 动作 |
|---|---|---|
| < 30% | 健康，有余量 | 什么都不用做 |
| 30~70% | 开始有压力 | 观察 p99，准备分片方案 |
| > 70% | 快到墙了 | 先降 tick 频率或减负载；接下来必须分片（按 sessionId 哈希分到多个泵） |

`/stats` 里还有 `rejectedByLimit`（会话数上限拒绝）和每会话的 `waitSnd` / `dropped`（背压与限流是否触发）。

## 6. 要做严肃容量评估，还得补什么

1. **两台机器**：生成器与服务端分开，用真实网卡（排除 CPU 争抢与 loopback 特性）。
2. **生成器多进程**：单进程多线程仍受 GC 与调度影响，能力上限约 1-2 万 msg/s。
3. **加真实业务**：现在的 echo 只有一次 JSON 往返；真实玩法会查表、算伤害、写库。
4. **长稳测试**：跑 1~24 小时看内存曲线（会话回收、缓冲池、KCP 段池是否泄漏）。
5. **按连接数而非消息数再测一轮**：挂 5 千~1 万空闲会话（只发心跳），看每拍遍历成本。

```bash
# 终端 2：三轮对照
dotnet run --project tests/EFramework.Tests -- load 127.0.0.1 7777 --clients 100 --qps 10  --seconds 10 --stats-url http://127.0.0.1:8080/stats
dotnet run --project tests/EFramework.Tests -- load 127.0.0.1 7777 --clients 100 --qps 100 --seconds 10 --mode ping --stats-url http://127.0.0.1:8080/stats
dotnet run --project tests/EFramework.Tests -- load 127.0.0.1 7777 --clients 800 --qps 12.5 --seconds 10 --mode ping --threads 4 --stats-url http://127.0.0.1:8080/stats
```
